3. Вывод

Задание 3 (CLI-приложение): оба SAST-инструмента не выявили ни одного нарушения (0 срабатываний). Приложение использует только параметризованные запросы через psycopg2.sql, не имеет веб-интерфейса, не хранит состояния и не работает с сетевыми сокетами напрямую — вследствие этого поверхность атаки минимальна.

Задание 7 (Flask веб-приложение): оба инструмента зафиксировали по 1 нарушению — использование host="0.0.0.0" в app.run(). Оба инструмента указали на одну и ту же строку кода (242), подтвердив находку. Дополнительно ручной анализ выявил ещё одну потенциальную проблему — небезопасный fallback-ключ сессии Flask, — которую автоматические инструменты не смогли обнаружить.

Сравнительный вывод (Задание 3 → Задание 7):

  • Количество реальных нарушений, зафиксированных инструментами, увеличилось с 0 до 1 при переходе от CLI к веб-приложению.
  • Ложных срабатываний автоматических инструментов не выявлено: единственное найденное нарушение является реальным и подтверждено двумя независимыми инструментами.
  • Рост числа проблем обусловлен расширением поверхности атаки: добавление веб-интерфейса на Flask, работа с HTTP-сессиями, хранение учётных данных — это новые категории рисков, которых не было в CLI-приложении.
  • Автоматические инструменты эффективно нашли конфигурационную уязвимость сетевого уровня, однако пропустили проблему небезопасного секретного ключа по умолчанию — это указывает на ограниченность только автоматизированного анализа и необходимость ручного code review.

Общая рекомендация: при дальнейшем усложнении приложения (добавление аутентификации пользователей, ролей, файловых загрузок, API) следует ожидать дальнейшего роста числа предупреждений SAST. Рекомендуется интегрировать оба инструмента в CI/CD-пайплайн и проводить ручной анализ каждого нового модуля.
